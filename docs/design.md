# 设计文档

> 场景 1：购物车服务在网络分区时仍允许修改购物车。
> 关键词：CRDT、版本向量、冲突合并。

---

## 1. 问题与约束

需求里有两句话决定了整个设计：

1. **"网络分区时仍允许修改购物车"** —— 分区期间不能拒绝写。
   → 选 **AP**，少数派也继续接受写入。
2. **"同一用户可能同时使用手机和电脑，不能简单覆盖掉其中一端添加的商品"** ——
   冲突必须**合并**而不是**覆盖**。
   → 拒绝 LWW（最后写入者胜），也拒绝主从复制（会拒绝写或者覆盖）。

由 CAP：分区 + 允许写 ⇒ 放弃线性一致性。我们能提供的是：

- **最终一致性**：网络恢复后所有副本收敛；
- **因果一致性**：看到过的写不会丢（版本向量保证）；
- **并发写合并**：两端并发添加的商品都保留（OR-Set 保证）。

## 2. 系统模型与假设

| 维度 | 假设 | 说明 |
|---|---|---|
| 网络 | 异步、可分区、可重复、可乱序、可丢包 | 由 `fault.py` 注入 |
| 节点 | 崩溃-恢复模型（fail-stop + 重启） | 不假设瞬时恢复，WAL 负责 |
| 拜占庭 | 不考虑 | 课程范围外 |
| 时钟 | 各节点物理时钟可能漂移、回拨 | HLC 兜底，CRDT 不依赖 |
| 副本数 | 3（可扩到任意） | 多数派 = 2 |

**不假设**：消息不丢、消息有序、时钟同步、进程不崩溃。这四条全部拿掉，
系统仍然能收敛——这是 CRDT 的价值所在。

## 3. 为什么是 CRDT

| 方案 | 分区期间 | 并发添加同款商品 | 结论 |
|---|---|---|---|
| LWW（按时间戳取最大） | 能写 | **后写的覆盖先写的，另一端的商品消失** | ❌ 违反需求 |
| 主从复制 | 少数派**拒绝写** | 不会丢，但要求重试 | ❌ 违反"仍允许修改" |
| 2PC / 共识写 | 少数派**阻塞** | 一致 | ❌ 可用性不足，且延迟高 |
| **OR-Set（本方案）** | 两端都能写 | **并集 + 数量相加** | ✅ |

演示里把 LWW 当作对照组保留（`src/cart/lww.py`），在场景 8 中直观展示它如何
吞掉另一端的数据。

## 4. 数据结构与不变量

```
Cart(user) = { sku -> SkuEntry }
SkuEntry   = ( adds:   { Dot -> qty },
               removed: Set<Dot> )
Dot        = ( replica_name, seq )         # 全局唯一
可见数量    = Σ{ qty | dot ∈ adds 且 dot ∉ removed }
```

### 4.1 OR-Set 语义

- `add(sku, qty)`：生成新 `Dot`（本副本序号 +1），记入 `adds`；
- `remove(sku)`：把**此刻看得见的** dot 记入 `removed`（墓碑），不删数据；
- 并发 add 用的是**新 dot**，不在别人的墓碑里 ⇒ **add-wins**。

### 4.2 三个不变量

1. **dot 唯一性**：同一个 dot 永远携带同样的内容。复用或内容冲突都是 bug，
   `SkuEntry.add` 会直接抛 `ValueError`。
2. **墓碑单调**：`removed` 只增不减（除非做 GC）。因此先到的删除不会被后到的
   添加复活。
3. **合并是半格 join**：`adds` 求并、`removed` 求并，满足交换律、结合律、幂等律。

第 3 条是整个系统可收敛的根本原因，也是 `tests/test_convergence.py` 用
hypothesis 随机验证的对象。

### 4.3 为什么墓碑必须与到达顺序无关

最初的实现是"只在本地已有的 add 上打墓碑"，性质测试立刻发现了反例：
**删除消息先于对应的添加到达时，商品会复活**。真实网络不保证因果投递，
所以墓碑改为对"它点名的 dot"无条件生效。这一改动是场景 3 能通过的原因。

### 4.4 版本向量

每个副本维护 `vv: {replica -> max_seq}`：

- 反熵时告诉对端"我已经有什么"，对端只发缺的那部分；
- 判断两条写是**并发**还是有**先后**（`Op.happens_before`）；
- 恢复时判断断点（场景 5 的断点续传靠它，而不是位点）。

## 5. 通信协议

**拉模式反熵**，每隔 `SYNC_INTERVAL`（默认 0.5s）执行一次：

```
副本 A                                  副本 B
  |  POST /internal/pull  {vv: A.vv}  ->  |
  |  <-  {type:"ops",  ops:[...], more}   |
  |  逐条 apply（幂等）                    |
```

- **分页**：`limit` 控制单页大小，`more` 表示还有。分页让"迁移到一半宕机"
  天然可续传——已经 apply 的进了 WAL，`vv` 指示继续位置。
- **降级为全量状态**：如果 A 需要的操作已经被 B 的检查点覆盖（B 的日志裁剪过），
  B 改发 `{type:"state", carts, vv}`，A 直接做 CRDT 合并。合并是幂等的，
  因此状态传输与操作传输可以混用。

选择拉模式而不是推模式：拉模式自带流量控制（对端要多少给多少），
且接收方掌握自己的进度，天然幂等。

## 6. 持久化与崩溃恢复

`WriteAheadLog` = 单文件、一行一条 JSON、**检查点内嵌在同一个文件里**。

```
{"type":"op", ...}
{"type":"op", ...}
{"type":"checkpoint", "carts":..., "vv":..., "counter":..., "applied":[...]}
{"type":"op", ...}          <- 检查点之后的增量
```

恢复流程：顺序扫描 → 记住最后一个 checkpoint → 重放它之后的操作。

**为什么不用"快照文件 + 日志文件"两件套**：那样必须处理"快照写完但日志没截断"
"快照写了一半"等一致性问题。内嵌检查点只有一种状态机，恢复逻辑简单得多。

崩溃点分析：

| 崩溃时机 | 结果 |
|---|---|
| `append` 写了一半 | 半行 JSON，恢复时跳过。该操作从未回 ack，客户端不可见，正确 |
| `append` 完成、内存未更新 | 恢复时重放，操作生效。客户端可能没收到 ack 而重试，靠 `request_id` 去重 |
| 内存已更新、ack 未发出 | 同上 |

**写日志先于回 ack** 是这里唯一不能妥协的顺序。

### 6.1 幂等键

`Op.request_id` 由客户端生成，副本维护 `request_id -> Op` 映射。
重试同一个 `request_id` 直接返回原操作，不产生新 dot。

已知限制：这个去重表是**单副本**的。如果客户端重试时换了一个副本，
另一个副本并不知道这个 `request_id` 已经处理过。真实系统要么把客户端
粘在固定副本上（本实现的做法），要么把去重表也做成复制状态。
这条写在"已知限制"里，答辩时主动说明比被问出来好。

## 7. 结算：为什么必须换一套机制

购物车用 CRDT，但**下单结算不能用**。原因：结算要求"只成交一次"，
而 CRDT 的语义是"并发写都保留"——正好相反。

因此结算路径刻意做成 **CP**：

1. 一致性哈希选出该用户的**结算主副本**（`owner_name`）；
2. 请求必须路由到主副本（HTTP 层用 409 提示，真实系统由网关承担）；
3. 主副本必须能联系到**多数派**，否则拒绝结算（503）；
4. 主副本上做 CAS：`expected_version == cart.checkout_version` 才成交，成功后
   版本 +1，并以操作的形式复制给其它副本（`checkout` op，按 max 合并）。

于是同一份系统里同时存在两条路径：

| 路径 | 一致性 | 分区少数派 | 理由 |
|---|---|---|---|
| 购物车增删 | AP + 最终一致 | **照常可用** | 丢一次点击比拒绝服务更糟；冲突可以合并 |
| 下单结算 | CP + CAS | **拒绝服务** | 重复扣款是资损，宁可失败 |

这就是"为什么不能所有东西都用 CRDT"的答案。

已知限制：没有实现重新选主。主副本宕机时结算直接不可用（503），
真实系统需要 Raft/Paxos 或租约（lease + fencing token）来安全地换主。

## 8. 故障注入设计

注入点在**传输层**（`FaultInjector`），而不是业务逻辑里。好处：

- 进程内模式和 HTTP 模式共用同一套注入代码，结论不会因为换传输方式而失效；
- 故障是显式代码，可复现、可断言、可写进测试，而不是靠运维手动搞；
- 不需要特权容器，Windows / Docker Desktop 上都能一条命令跑。

代价与取舍：这不是内核级的真实丢包。真实分区可以用
`docker network disconnect` 复现（README 给了命令），两条路径应当得到一致的结论。
演示里选择应用层注入，是因为它**确定性**更好——答辩时能稳定复现，
不会因为偶发的时序差异翻车。

## 9. 正确性论证（要点）

**定理（收敛性）**：若网络最终恢复且消息最终送达，则所有副本的购物车状态相等。

证明要点：

1. 每个副本的状态是若干个 op 的 fold：`state = merge(op1, merge(op2, ...))`；
2. `merge` 是半格 join（交换、结合、幂等），由 `test_merge_is_*` 随机验证；
3. 反熵保证任意 op 最终被所有副本收到（拉模式 + 无限重试）；
4. 因此所有副本最终 fold 同一个 op 集合 ⇒ 状态相等。∎

**不变量**：任何时刻，某 SKU 的可见数量 = 全集群 `adds` 中未被任何 `remove`
点名的 dot 的 qty 之和。`test_converges_to_oracle_after_healing` 用这条
作为"预言机"，在随机故障历史下逐例核对。

**没有被证明的东西**（诚实声明）：

- 结算路径的线性一致性依赖"主副本唯一 + 多数派可达"，没有形式化证明；
- 分区期间可能出现"结算成功但客户端没收到回执"，重试会撞版本冲突，
  需要客户端读一次最新版本再决定——这是业务层的幂等设计问题，不在本实现范围。

## 10. 已知限制

| 限制 | 影响 | 真实系统怎么做 |
|---|---|---|
| 去重表是单副本的 | 换副本重试可能重复 | 复制去重表 / 客户端粘性路由 |
| 日志不裁剪 | 长期运行会无限增长 | 分段 + 水位线 + GC |
| 墓碑不 GC | 状态随删除次数增长 | 因果稳定性（causal stability）后清理 |
| 无重新选主 | 主副本宕机则结算不可用 | Raft / lease + fencing token |
| 全量状态传输无压缩 | 大购物车迁移较慢 | Merkle 树差分、增量快照 |
| 热点分片未实现 | 单 key 读扩展受限 | 拆成 N 个计数副本 |

这些不是"没做完"，而是**明确划出的边界**——写清楚比假装没有更有说服力。

## 11. 典型提问的标准答案

**Q：这行版本比较代码删掉会怎样？**
删掉 `expected_version != current` 的检查，CAS 退化成无条件写：两个并发结算
都会成功，产生重复扣款。购物车侧对应的版本比较是 `SkuEntry.merge_with` 里的
dot 一致性检查，删掉后同一个 dot 可能携带不同数量，合并结果取决于到达顺序，
不再满足交换律。

**Q：写入成功究竟表示多少个节点已保存？**
取决于路径。购物车写入 `acks=1`：本副本 WAL fsync 即返回，其余副本异步反熵；
所以"成功"= **只有 1 个节点持久化**，别人可能还看不到。结算写入要求主副本 +
多数派可达（2/3），但仍然只有主副本写入，只是"能联系到多数派"作为安全前提。

**Q：哪段执行可以让客户端读到旧值？**
`GET /cart/{user}` 只读本地状态，不等待反熵。分区期间或反熵周期之间，
客户端读到的就是旧值。这是 AP 的固有代价，不是 bug。

**Q：如果 quorum 从 2 改成 1，会失去什么？**
失去"结算时能联系到多数派"这道保险。主副本被隔离到少数派时仍会接受结算，
而多数派那边可能已经选了新主并完成另一次结算 ⇒ 两次结算都成功 ⇒ 重复扣款。
quorum=1 等于放弃 CP，退化成单点。

**Q：为什么不能只用物理时钟解决冲突？**
物理时钟既会漂移也会回拨（场景 8 直接演示了倒退一分钟）。更重要的是，
时间戳只能给出全序，无法区分"因果先后"和"并发"——两个并发的写谁大谁小
纯属偶然，用它做覆盖就会丢数据。版本向量能精确表达"我见过你的写"，
这是时间戳做不到的。

**Q：刚才失败请求的 happens-before 关系是什么？**
`Op.ctx` 记录了发起时的版本向量。若 `op_b.ctx` 包含 `op_a.origin`，则
`a happens-before b`；否则两者并发。失败的那次结算与成功的那次是**并发**的吗？
不是——它们都读到了同一版本 `v`，且互相不知道对方，因此是**并发**关系，
这正是 CAS 必须串行化到同一个主副本的原因。

**Q：为什么购物车不用 CAS，结算不用 CRDT？**
见第 7 节。一句话：购物车的冲突可以合并（并集），结算的冲突不能合并（只能二选一）。
