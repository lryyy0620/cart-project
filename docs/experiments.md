# 实验记录：9 个故障场景

> 复现命令：`python -m cart.runner`（全部）或 `python -m cart.runner --scenario 3`。
> 每个场景都按作业要求的四步组织：**预测 → 注入 → 对照 → 解释**。

## 总览（本机实测）

```
编号  场景                          检查   耗时     结果
1     一个副本突然宕机              3/3    ~0ms    PASS
2     双向分区，消息被重复发送三次  4/4    ~0ms    PASS
3     消息延迟 0.3 秒后乱序到达     4/4    ~600ms  PASS
4     节点重启后丢失内存状态        4/4    ~20ms   PASS
5     新节点在数据迁移到一半时宕机  5/5    ~20ms   PASS
6     某个 key 占据 50% 的请求      4/4    ~5ms    PASS
7     两个客户端同时执行 CAS        3/3    ~0ms    PASS
8     系统时间突然倒退一分钟        3/3    ~0ms    PASS
9     磁盘写成功，但响应在途中丢失  5/5    ~20ms   PASS
```

场景 3 默认把 10 秒压缩成 300ms，避免每次回归都等 20 秒；用
`--slow` 可以跑真实的 10 秒延迟。

## 场景 1：一个副本突然宕机

**预测**：宕机期间另外两个副本继续可写；宕机副本重启后靠反熵补齐；最终一致。

**注入**：`r2.set_down(True)` → 在 r1、r3 各写一条 → `set_down(False)` → 反熵。

**实际**：

| 检查项 | 预期 | 实际 |
|---|---|---|
| 宕机副本未收到新写入 | `{咖啡豆:2, 燕麦奶:1}` | 同左 |
| 重启后补齐全部数据 | 4 个 SKU | 4 个 SKU |
| 三副本最终一致 | True | True |

**结论**：AP 路径下副本失效不影响可用性。补齐走的是"对方版本向量里缺什么就发什么"，
因此不会重复计数。

---

## 场景 2：双向分区，消息被重复发送三次

**预测**：两侧各写各的；同款商品恢复后数量相加；重复三份不翻倍。

**注入**：`partition({r1,r2}, {r3})` → 两侧各写"苹果"（1 和 2）→ 恢复 →
`duplicate = 3` → 反熵。

**实际**：

| 检查项 | 预期 | 实际 |
|---|---|---|
| 分区两侧各写各的 | `({"苹果":1}, {"苹果":2})` | 同左 |
| 恢复后数量相加 | `{"苹果":3}` | `{"苹果":3}` |
| 重复消息被幂等拦下 | True | True（拦下 6 次） |
| 三副本一致 | True | True |

**结论**：重复投递被"同一个 origin 只应用一次"拦住；数量相加而不是覆盖，
是 OR-Set 的直接结果。

---

## 场景 3：消息延迟 10 秒后乱序到达

**预测**：延迟期间读到陈旧值；乱序不会让已删除的商品复活；延迟消除后收敛。

**注入**：`latency_ms=300`（`--slow` 时为 10000）、`reorder_window_ms=1.0`
触发投递顺序打乱；先断开两副本，各写一条，再恢复。

**实际**：

| 检查项 | 预期 | 实际 |
|---|---|---|
| 延迟期间读到陈旧值 | `{"咖啡豆":2}` | 同左 |
| 乱序后两件商品都在 | `{"咖啡豆":2, "苹果":3}` | 同左 |
| 延迟真实发生 | True | True（实测 602ms） |
| 两副本收敛 | True | True |

**结论**：这条是**改过实现**才过的。最初"只在本地已有的 add 上打墓碑"，
删除先到时会失效，商品复活。改为"墓碑对点名的 dot 无条件生效"后，
合并与到达顺序无关，性质测试才能通过。

---

## 场景 4：节点重启后丢失内存状态

**预测**：内存全丢但 WAL 还在，重启后完整恢复（状态、版本向量、本地计数器）。

**注入**：写两条 → `checkpoint()` → 再写一条 → `close()`（等价 kill）→
新建 `Replica` 指向同一 WAL。

**实际**：

| 检查项 | 预期 | 实际 |
|---|---|---|
| 恢复出全部数据 | 3 个 SKU | 同左 |
| 版本向量一致 | `{r1:3}` | `{r1:3}` |
| 本地计数器一致 | 3 | 3 |
| 重放检查点之后的增量 | 1 | 1 |

**结论**：检查点 + 增量重放。**踩过的坑**：恢复时如果只从检查点装载计数器、
不把重放操作的序号推上去，重启后新 op 会复用旧 dot——`_apply_only` 里那句
`self.counter = max(self.counter, op.origin.seq)` 就是为这个加的。

---

## 场景 5：新节点在数据迁移到一半时宕机

**预测**：分页迁移，第一页后被杀；重启后从版本向量指示的位置继续；
最终与源一致，不丢不重。

**注入**：源副本 12 条操作 → 新副本 `join_from(page_size=3, pages=1)`
主动抛出 `MigrationInterrupted` → 重启新副本 → 继续迁移。

**实际**：

| 检查项 | 预期 | 实际 |
|---|---|---|
| 迁移确实被中断 | True | True |
| 中断时只拿到部分数据 | True | True |
| 重启后补齐 | 与源一致 | 与源一致 |
| 没有重复计数 | 12 | 12 |
| 已迁移部分无需重放 | 3 | 3 |

**结论**：断点续传不需要额外的位点表——版本向量本身就是"我收到了什么"的压缩表示。

---

## 场景 6：某个 key 占据 50% 的请求

**预测**：热点 key 的写入全部成功、数量精确；CRDT 下热点没有写冲突；
同样热点用 CAS 串行化则 5 个并发只成功 1 个。

**注入**：200 次写入，其中 100 次打在同一个 SKU 上，跨两个副本；然后对同一
用户连发 5 次 `checkout(expected_version=0)`。

**实际**：

| 检查项 | 预期 | 实际 |
|---|---|---|
| 热点写入次数 | 100 | 100 |
| 热点 key 数量精确 | 100 | 100 |
| 热点写入零失败 | True | True |
| CAS 串行化下只有 1 个成功 | (1, 4) | (1, 4) |

**结论**：CRDT 的每次 add 自带独立 dot，热点 key 上不存在"读-改-写"的竞争窗口，
所以 50% 的流量打在一个 key 上也不会互相冲突。反过来说，一旦需要"只成交一次"
（CAS），同一个 key 就会变成串行化瓶颈——这正是场景 7 的代价。

---

## 场景 7：两个客户端同时执行 CAS

**预测**：同一版本号的两个结算只有一个成功；失败方收到明确的版本冲突；
分区时若主副本联系不到多数派，结算被拒但购物车仍可写。

**注入**：选一个主副本是 r3 的用户，连发两次 `checkout(0)`；然后把 r3 隔离到少数派。

**实际**：

| 检查项 | 预期 | 实际 |
|---|---|---|
| 并发 CAS 结果 | `[成功@v1, 冲突(实际v1)]` | 同左 |
| 分区期间购物车仍可写 | True | True |
| 分区期间结算被拒绝（CP） | True | True |

**结论**：同一份系统里两条路径的取舍可以完全不同：
购物车要可用性，结算要正确性。

---

## 场景 8：系统时间突然倒退一分钟

**预测**：LWW 会吞掉慢时钟一侧的写入；HLC 在时钟倒退后仍单调；CRDT 不受影响。

**注入**：LWW 对照 —— 快时钟侧写"苹果×1"（时间 T），慢时钟侧写"苹果×2"（T-60s）；
HLC —— `Clock(offset=-60000)`；CRDT —— 两副本各加一次。

**实际**：

| 检查项 | 预期 | 实际 |
|---|---|---|
| LWW 吞掉了慢时钟侧的数量 | 1 | 1 |
| HLC 时钟倒退后仍单调 | True | True |
| CRDT 不受时钟影响 | `{"苹果":3}` | `{"苹果":3}` |

**结论**：物理时钟既会回退，也无法表达因果。这是"为什么不能只用物理时钟解决冲突"
的可执行答案。

---

## 场景 9：磁盘写成功，但响应在途中丢失

**预测**：服务端已落盘并生效；客户端用同一 `request_id` 重试不会累加；
重启后去重表能从 WAL 重建。

**注入**：`add(苹果×2, request_id=R)` → 同一 `request_id` 再发一次（模拟重试）→
`close()` → 重启 → 扫描 WAL。

**实际**：

| 检查项 | 预期 | 实际 |
|---|---|---|
| 重试后数量不翻倍 | 2 | 2 |
| 重试返回同一条操作 | True | True |
| 被识别为重复请求 | 1 | 1 |
| 重启后数量依旧正确 | 2 | 2 |
| WAL 里该请求只有一条 | 1 | 1 |

**结论**：去重表不需要单独持久化——`request_id` 写在操作里，重放即重建。

## HTTP 端到端（三进程真实网络）

除进程内场景外，还有一条真实 HTTP 路径：

```powershell
python scripts/local.py start      # 或 docker compose up --build -d
python scripts/demo_http.py
python scripts/local.py stop
```

实测输出（10/10 通过）：

```
1) 探测副本                r1/r2/r3 up=True
2) 正常情况下双端写入      三副本 {咖啡豆:2, 燕麦奶:1}
3) 制造分区 {r1,r2}|{r3}   r1={...,苹果:1}  r3={...,苹果:2}
4) 恢复 + 重复投递三份     三副本 {咖啡豆:2, 燕麦奶:1, 苹果:3}
5) 结算 CAS               第一次 200，第二次 409
6) 分区时结算             结算 503，购物车写入仍 200
```

这条路径验证的是"换个传输层结论不变"：故障注入逻辑在 `FaultInjector` 里，
进程内和 HTTP 共用同一套。
